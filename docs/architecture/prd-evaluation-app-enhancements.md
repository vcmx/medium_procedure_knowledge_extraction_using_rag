# PRD: Evaluation App Enhancements

## 1. Overview

This document outlines the requirements for enhancing the RAG Evaluation Streamlit App (`run_evaluation_app.py`). The primary goal is to improve its testing capabilities by adding feature parity with the main chat application (`rag_chat_app.py`) and introducing a more robust system for managing and storing test case results for different Large Language Models (LLMs).

## 2. Goals

- **Feature Parity:** Integrate LLM selection into the evaluation app, similar to the main chat app.
- **Advanced Test Management:** Upgrade the test case management system to handle and store evaluation results (outputs and scores) on a per-LLM basis.
- **Improved UI/UX:** Redesign the test case management interface to clearly display complex, multi-LLM results using a master-detail view.
- **Persistent Evaluation History:** Enable the system to save evaluation results back into the test case file, providing a historical record of performance for each LLM.

## 3. User Stories

- **As a developer, I want to** select a specific LLM from a list to run an evaluation against, so that I can test the performance of individual models.
- **As a developer, I want to** see the `actual_output` and evaluation `scores` for each LLM I run a test case against, so that I can compare their performance directly.
- **As a developer, I want** the evaluation results for each LLM to be saved, so that I can track performance improvements or regressions over time.
- **As a developer, I want** a clear and organized interface to view all test cases and their detailed, per-LLM results without clutter.

## 4. Functional Requirements

### 4.1. LLM Selection in Evaluation App

1.  The evaluation app (`run_evaluation_app.py`) must include a dropdown menu to select the LLM for running an evaluation.
2.  The list of LLMs should be consistent with the one in `rag_chat_app.py` (i.e., `meta-llama/llama-4-maverick`, `anthropic/claude-3.7-sonnet`, `google/gemini-2.5-pro-preview`).
3.  The user must be able to run an evaluation for one selected LLM at a time.

### 4.2. Test Case Data Structure

1.  The JSON file for test cases (`evaluation_test_cases.json`) must be updated to support a new structure.
2.  Each test case object will contain a new key, `evaluation_results`.
3.  The `evaluation_results` object will store results nested under the specific LLM's name (e.g., `"meta-llama/llama-4-maverick"`).
4.  For each LLM, the stored data must include:
    -   `actual_output` (string): The response generated by the RAG system using that LLM.
    -   `scores` (object): A dictionary of evaluation metrics and their scores (e.g., `{"relevance": 1.0, "coherence": 0.9}`).
    -   `last_evaluated` (string): An ISO 8601 timestamp of when the evaluation was last run.
5.  There should be a single, universal `expected_output` field at the top level of the test case object. This will be used as the ground truth for evaluation across all LLMs.

**Example JSON Structure:**

```json
[
  {
    "name": "My Test Case",
    "input": "What is the primary function of the flux capacitor?",
    "expected_output": "It's what makes time travel possible.",
    "evaluation_results": {
      "meta-llama/llama-4-maverick": {
        "actual_output": "The flux capacitor enables temporal displacement.",
        "scores": {
          "relevance": 1.0,
          "coherence": 0.9
        },
        "last_evaluated": "2024-07-29T10:00:00Z"
      },
      "google/gemini-2.5-pro-preview": {
         "actual_output": "It's the core component for time travel.",
         "scores": {
          "relevance": 0.9,
          "coherence": 1.0
         },
         "last_evaluated": "2024-07-29T10:05:00Z"
      }
    }
  }
]
```

### 4.3. Test Case Management UI

1.  The "Test Case Management" tab will be redesigned from a simple editable table into a master-detail view.
2.  **Master View:**
    -   A list or compact table will display all test cases, showing key information like `name` and `input`.
    -   This view will allow for adding new test cases and deleting existing ones.
3.  **Detail View:**
    -   Clicking a test case in the master view will display its full details.
    -   This view will show the `input` and `expected_output` fields.
    -   It will also display the `evaluation_results` in a structured way, perhaps using tabs or expandable sections for each LLM that has been evaluated.
    -   For each LLM result, it should clearly show the `actual_output`, the `scores`, and the `last_evaluated` timestamp.
4.  The "Save Changes" functionality will persist any modifications to the test cases, including the new `evaluation_results`, back to the JSON file.

## 5. Non-Goals (Out of Scope)

-   Running evaluations for multiple LLMs simultaneously in a single run.
-   Making the LLM list dynamically configurable from an external file in this iteration. The hardcoded list is acceptable for now.
-   Complex historical trend analysis or visualization of scores over time.

## 6. Technical Considerations

-   The `st.data_editor` might not be suitable for the master-detail view; a custom implementation using columns, containers, or session state to manage the selected item will be necessary.
-   Careful state management will be required in Streamlit to handle the selection in the master view and update the detail view accordingly.
-   The file I/O logic (`load_test_cases`, `save_test_cases`) will need to be robust to handle the new, more complex JSON structure and potential missing keys in older data.

## 7. Success Metrics

-   The evaluation app successfully runs evaluations using a selected LLM.
-   Evaluation results, including `actual_output` and `scores`, are correctly saved back to the JSON file under the corresponding LLM key.
-   The new master-detail UI for test case management is functional and provides a clear view of per-LLM results.
