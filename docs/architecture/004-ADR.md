# ADR 004: FalkorDB Integration for Graph and Vector Storage

## Status

Proposed

## Context

The current system uses ChromaDB for vector storage of document chunks, providing similarity search capabilities. However, technical manuals often have complex relationships between chunks (procedural dependencies, part references, safety warnings) that would benefit from a graph-based storage solution. Additionally, maintaining separate databases for vector and graph operations adds complexity and potential consistency issues.

## Decision

We propose to replace ChromaDB with FalkorDB, a Redis-based graph database that supports both vector and graph operations. This will provide a unified storage solution for both vector embeddings and graph relationships between chunks.

## Consequences

### Positive

1. **Unified Storage Solution**
   - Single database for both vector and graph operations
   - Simplified architecture
   - Better consistency guarantees
   - Reduced operational complexity

2. **Enhanced Query Capabilities**
   - Combined vector similarity and graph traversal
   - Support for complex relationship queries
   - Real-time updates and queries
   - Efficient hybrid search

3. **Better Representation of Technical Manual Structure**
   - Natural graph representation of procedural dependencies
   - Efficient storage of cross-references
   - Support for complex relationships between chunks
   - Better handling of part numbers and their usage

4. **Performance Benefits**
   - Redis-based performance
   - Efficient for both graph and vector operations
   - Good for real-time operations
   - Reduced network overhead

### Negative

1. **Migration Complexity**
   - Need to migrate existing data from ChromaDB
   - Potential downtime during migration
   - Need to update existing queries

2. **Learning Curve**
   - New database to learn and maintain
   - Different query patterns to understand
   - Need to train team on new technology

3. **Potential Limitations**
   - May need to optimize for specific use cases
   - Different scaling characteristics
   - Need to monitor performance

## Implementation Details

1. **Data Structure**
   ```python
   class FalkorNode:
       id: str
       text: str
       embedding: List[float]
       metadata: Dict[str, Any]
       images: List[Tuple[str, str]]  # (image_path, caption)

   class FalkorEdge:
       source: str
       target: str
       type: str  # e.g., "depends_on", "references", "safety_warning"
       properties: Dict[str, Any]
   ```

2. **Integration Points**
   - CLIP for generating embeddings
   - RAPTOR for chunking and hierarchy
   - Existing query interface
   - Migration tools

3. **Query Patterns**
   ```python
   # Vector similarity search
   def vector_search(query_embedding: List[float], limit: int) -> List[FalkorNode]

   # Graph traversal
   def find_dependencies(node_id: str) -> List[FalkorNode]

   # Hybrid search
   def hybrid_search(query_embedding: List[float], relationship_type: str) -> List[FalkorNode]
   ```

## Alternatives Considered

1. **Keep ChromaDB + Add Separate Graph DB**
   - Pros: No migration needed, can use specialized tools
   - Cons: More complex architecture, consistency challenges

2. **Use Neo4j + Vector Plugin**
   - Pros: Mature graph database, good tooling
   - Cons: Less integrated vector support, higher overhead

3. **Use ArangoDB**
   - Pros: Multi-model database, good documentation
   - Cons: Less specialized for vector operations
