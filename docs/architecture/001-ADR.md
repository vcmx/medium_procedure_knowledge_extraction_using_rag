# PDF Processing System - Architecture Decision Record

## Context

We need to process technical PDF documents while maintaining the relationship between text and images, and create a searchable knowledge base. The system must handle hierarchical content, step-by-step procedures, and maintain context between chunks.

## Decision

We will implement a modular system with the following components:

1. PDF Processing Module (Marker)
2. Image Captioning Module (Florence-2)
3. Text Processing Module (Custom)
4. Storage and Retrieval Module (ChromaDB + CLIP)

## Status

Accepted

## Consequences

### Positive

1. **Modular Architecture**
   - Each component can be updated independently
   - Easy to test individual components
   - Clear separation of concerns

2. **Context Preservation**
   - Maintains relationships between text and images
   - Preserves document structure
   - Supports hierarchical navigation

3. **Scalable Storage**
   - ChromaDB provides efficient vector storage
   - CLIP embeddings enable semantic search
   - Metadata supports rich querying

4. **Flexible Processing**
   - Supports various PDF structures
   - Handles multiple images per chunk
   - Maintains step-by-step procedures

### Negative

1. **Processing Overhead**
   - Florence-2 model is resource-intensive
   - CLIP embeddings require significant computation
   - Large PDFs may take time to process

2. **Storage Requirements**
   - Images and embeddings require significant storage
   - Metadata overhead for each chunk
   - Need for efficient storage management

3. **Complexity**
   - Multiple components to maintain
   - Need for careful error handling
   - Complex state management

### Data Flow

1. PDF → Marker → Text + Images
2. Images → Florence-2 → Captions
3. Text + Captions → Chunking → Chunks
4. Chunks → CLIP → Embeddings
5. Embeddings + Metadata → ChromaDB

### Key Decisions

#### 1. Chunking Strategy

- Chunks are created at section boundaries
- Each chunk includes:
  - Current section text
  - Associated images and captions
  - Section hierarchy
  - Page number
  - Metadata

#### 2. Image Processing

- Images are processed using Florence-2
- Captions are stored with their chunks
- Image paths are maintained for reference

#### 3. Storage Strategy

- ChromaDB for vector storage
- CLIP for embeddings
- Metadata for rich querying
- Efficient chunk management

## Alternatives Considered

### 1. Alternative Chunking Strategies

- **Fixed-size chunks**: Rejected due to context loss
- **Sentence-based chunks**: Rejected due to structure loss
- **Paragraph-based chunks**: Rejected due to context fragmentation

### 2. Alternative Storage Solutions

- **Elasticsearch**: Rejected due to complexity
- **PostgreSQL + pgvector**: Rejected due to maintenance overhead
- **Simple file storage**: Rejected due to search limitations

### 3. Alternative Image Processing

- **BLIP**: Rejected due to lower accuracy
- **CLIP-only**: Rejected due to lack of detailed captions
- **Manual captioning**: Rejected due to scalability issues
